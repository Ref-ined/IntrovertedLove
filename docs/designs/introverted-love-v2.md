# Design: Introverted Love v2 — a coaching composer for the partner who goes quiet

Generated by /office-hours on 2026-11-17

Repo: local, not yet on a remote
Status: APPROVED

## Problem Statement
Couples hurt each other with words in two opposite ways:
- **Going quiet:** the anxious partner stays silent instead of saying something hard, because they fear how their partner will react. The silence builds into distance or a later blow-up.
- **Lashing out:** in an argument, a partner texts something on impulse, out of anger, that they don't really mean. Once it's read, it can't be taken back.

Introverted Love sits between the two partners. Every message is translated into a humbler, kinder version that fits the recipient's questionnaire answers, so angry or clumsy words don't land as wounds. Paid users also get coaching, which helps the sender find their own words before sending. v2 rebuilds the app from scratch in a new folder and keeps what v1 proved.

## Demand Evidence
None yet. The founder confirmed there is no evidence that anyone wants this: no real couples have used v1 outside test accounts, and nobody has asked for it. This is the biggest risk, ahead of any engineering risk. The rebuild should make the first real conversation cheap to reach, not grow features around it.

## Status Quo
The target user stays silent or avoids the topic (founder's answer). The cost is relational, not financial: built-up resentment, distance, or a later fight. The real competitor is "saying nothing", not ChatGPT or another app.

## Target User & Narrowest Wedge
- **User:** the anxious attacher. They are scared of their partner's reaction, over-think every message, and end up sending nothing or something unclear. They're also the partner most hurt by an angry text in a fight.
- **Wedge:** one screen, the "Say it" composer.
  - **Free:** type it, and it's delivered as a humble translation. The sender sees exactly what went through.
  - **Paid:** "How will this land?" coaching first, so the sender finds their own words.
  - Everything else (diary, reports) is secondary to one hard or heated message landing softly instead of hurting.

## Constraints
- Must later ship as Android and iOS apps, so the backend has to be an API usable by a mobile client, not web-only server actions.
- Sign-in stays Clerk, with the 18+ age gate kept from v1.
- Single founder. Local dev runs on Windows with Node 26.
- The v1 audit fixes, restated for v2's coaching model, must hold by construction or by test:
  - **What the recipient receives:** the delivered text, which is the translation for a translated message or the sender's own words otherwise. The original is stored, because the sender may share it later. It's returned to the recipient only if the sender shared it **and** the recipient has paid access. Unsent drafts are saved only on the sender's device. Coaching and translation send text to Anthropic for that one request only. The server never logs it, and drafts and coaching suggestions are never stored or returned to the recipient.
  - **When the AI fails:**
    - **Translation:** nothing is sent. The sender sees "We couldn't soften this right now," with Retry or "Send my words as written." Text is never sent unsoftened without the sender's explicit choice (the v1 audit fix).
    - **Coaching:** the panel shows "Suggestions aren't available right now. You can still send your own words." Sending is never blocked, and the AI never sends or changes text on its own.
  - Free limits are atomic, billing events apply once, partner codes can't be guessed, and all input is validated at the API.
- **Secrets:** v1's Clerk, Emergent and VAPID keys were flagged as exposed. They must be rotated before v2 uses any of them. The v2 repo commits only `.env.example`, and `.env*` is gitignored from the first commit.

## Premises
1. **Agreed:** design for the anxious sender. The job is getting them from silence to a sent message.
2. **Modified by founder:** both models, split by plan.
   - **Free:** automatic translation, where the AI rewrites the message using the recipient's questionnaire. It's limited to the first 5 messages; after that, free messages are sent untranslated.
   - **Paid:** coaching, where the AI shows how the draft may land and offers swaps the sender picks.
   - **Risk kept on purpose:** a single hypothetical-friend study (Ohio State, 2023) suggests recipients see AI-polished messages as lower effort. Treat this as a hypothesis to watch during the Assignment, not a settled fact.
3. **Rejected by founder:** single-player and share-by-link. Both partners use the app, messaging stays in-app, and two-sided adoption remains an accepted risk.
4. **Modified by founder:** remove read receipts and typing indicators, keep streaks.
5. **Agreed:** keep Clerk, the 18+ gate, the questionnaire as AI context, and the audit fixes. Simplify pricing to Free plus one paid plan that covers both partners.
6. **Founder decision, originals:** a message's original words are never shown to the recipient automatically. The sender can later choose to share the original of any message they sent, and the recipient can read shared originals only on the paid plan. This protects anything said in anger: it stays softened unless the sender decides otherwise.

## Approaches Considered
- **A: Port and reshape v1** (React CRA + FastAPI + MongoDB). Fastest, but keeps deprecated Create React App, MongoDB's lack of constraints (the source of most races) and the Emergent proxy lock-in.
- **C: Keep Python, swap the weak parts.** Fixes the database and lock-in problems but still means two apps, two languages and two deploys.
- **B: One TypeScript app (chosen)**, described below.

## Recommended Approach
**B, built API-first, in two milestones.** The founder asked for "the best" and a mobile app after the web launch. Demand is unproven, so the build is ordered so that the first real conversation comes before monetization.

**Milestone 1 (M1): the Assignment build.** Sign-up with Clerk and the 18+ gate, pairing, the questionnaire, the composer (translation, heated-message breath step, coaching, sharing originals), and in-app messaging that refreshes by short polling. Paid access in M1 comes from a `plan` field that an admin script can set. That lets the first testers try coaching before Stripe exists. This is what the founder puts in front of the first 3 users.

**Milestone 2 (M2): after the product signal.** Stripe Subscriptions setting the `plan` field, realtime updates and push notifications, streaks, the diary and the weekly report. M2 starts when M1 is done and has been used by real users. The founder can choose to build both milestones in one go, but M1 must work end to end on its own.

**Plans**

| | Free | Paid (one plan covers both partners) |
|---|---|---|
| Messages | Unlimited | Unlimited |
| Automatic translation | First 5 messages (lifetime), then sent untranslated | Every message |
| Sender sees "what went through" | Yes | Yes |
| Coaching ("How will this land?") | No | Yes |
| Read the partner's shared originals | No | Yes |

**Translation (M1)**
- **Usage:** each send uses one translation. Free users' 5 lifetime translations are reserved in one database step, so parallel sends can't exceed them, and a failed translation gives its slot back. After 5, the composer shows "Your free translations are used up. Messages now send as written. Upgrade to keep them softened," and sends untranslated.
- **Heated messages:** the model returns a `heated` flag for angry or impulsive drafts. When it's set, the composer shows a breath step before sending: "This will be delivered as: [translation]", with Send, Edit, or Save for later. Save for later keeps the draft on the device.
- **Sharing originals:** on any message they sent, the sender can tap "Share my original words". This can be undone. The recipient sees the shared original only on the paid plan; otherwise they see "Your partner shared their original words. Upgrade to read them."

**Coaching (M1, paid)**
- **One pass = one AI call** for a draft text it hasn't seen before. A pass runs when the sender taps "How will this land?". There is no automatic coaching on every pause, so a single message can't use up a day's allowance.
- **Caching (on the device only):** the composer remembers the last result for each draft hash and doesn't call again for unchanged text. The server keeps no cache and counts every call it receives as a pass, so nothing about drafts or suggestions is stored server-side.
- **Access:** coaching is paid-only. Free users see the "How will this land?" button with an upgrade prompt. Paid passes aren't metered in v2; a fair-use cap can be added later if AI costs need it.
- **Response:** the model returns structured output: one "how this might land" line, 0-3 phrase swaps (each an exact span of the draft plus a replacement), a short encouragement, and a safety flag.
- **Safety:** if the draft suggests the sender may be unsafe (threats, abuse, coercive control, self-harm), the model sets `safety` instead of coaching. The UI then shows no softening suggestions, says plainly that their safety matters more than wording, and links to support resources. Prompt fixtures with representative drafts are tested.

**Pairing (M1)**
- **Code:** each user has a 10-character code drawn from a 31-symbol alphabet with no look-alike characters (about 49 bits). It's single-use, replaced once used, and expires after 7 days.
- **Rate limit:** code entry is limited to 10 attempts per hour per user.
- **One partner each:** a couple row with a unique constraint on each member, so each user can be in at most one active couple.
- **Unpairing:** ends the couple. Both people keep read-only access to their past conversation, and the streak ends. Paid access follows the billing rules below.

**Billing (M2)**
- **Subscriptions belong to the person who pays.** A user has paid access if their own Stripe subscription is `active` or `trialing`, or if their current partner's is. Being in a couple only *extends* the payer's plan to the partner. The Stripe webhook is the only writer of subscription state, and every event is stored by ID so it's applied once.
- **Checkout** is refused if the user already has paid access, whether their own or their partner's, which prevents new double payment.
- **Two subscribers who pair** (both paid before connecting) both stay paid. The app tells each of them one subscription is now enough and links to Stripe's billing portal to cancel the extra one. Nothing is cancelled automatically.
- **Cancellation:** paid access lasts until the period ends. A failed renewal (`past_due`) keeps access through Stripe's retry window, then that payer and any partner who relied on them drop to Free.
- **Unpairing:** the payer keeps their own subscription. The former partner loses the access they had through the payer.

**Streaks (M2)**
- A streak counts consecutive days, in the couple's time zone, on which either partner sent at least one message. It's shown small, to both partners.
- When it breaks, it quietly restarts at 0 with no loss message and no notifications about streaks. Calm UX comes first.

**Realtime (M2):** M1 uses polling: every 5 s while the conversation is open, 30 s otherwise. M2 adds push-based updates through a hosted realtime service or Postgres LISTEN/NOTIFY, depending on the host. Clients reconnect and fetch anything missed since the last message ID. Web Push on iOS only works for an installed PWA, so iOS users get reliable notifications from the native app later.

**Privacy and data flow**
- **What the AI receives:** the current draft text and the recipient's questionnaire traits (labels such as "needs reassurance", no names or emails).
- **Drafts** are saved only on the sender's device. They pass through the server to Anthropic once per coaching pass, without being stored or logged. AI suggestions are not stored server-side.
- **What's stored:** sent messages (the original, the delivered text and whether the original was shared), questionnaire answers and the couple record, all in Postgres. Originals are visible only to their sender until shared.
- **Account deletion** removes the user's messages, answers and pairing.
- **Disclosure:** the first time someone uses the composer, it tells them that drafts are processed by an AI provider (Anthropic) to make suggestions.
- **Recipient consent:** before someone answers the questionnaire, it says that their answers are turned into trait labels and sent to an AI provider (Anthropic) to help coach messages their partner writes to them. They choose to share or not share. If they don't share, no traits are sent and coaching uses neutral defaults. They can change this later in Settings.

**Architecture**
- **Monorepo** (pnpm workspaces): `apps/web` is Next.js (App Router), and `packages/core` holds the domain logic, database schema, validation (zod), coaching prompts and shared types. A future `apps/mobile` (Expo) reuses `packages/core` and the same API.
- **API:** `/api/*` route handlers taking JSON and Clerk bearer tokens, so the same endpoints serve web and mobile.
- **Data:** Postgres through a typed ORM. Unique constraints and transactions enforce limits, pairing and billing idempotency.
- **AI:** the Anthropic SDK called directly with the founder's own key (no Emergent proxy). It returns structured output (land-assessment line, phrase suggestions, confidence nudge).
- **Billing (M2):** Stripe Subscriptions with real monthly renewal and a webhook as the source of truth. One paid plan covers both partners (rules above).
- **Realtime:** polling in M1, push-based updates in M2 (see above).
- **Calm UX:** no read receipts and no typing indicators. Delivered status only. A gentle streak is kept (M2).
- **Wireframe:** projects/INtrovertedlove/refined-v2-sketch-20261117-141336.png (composer, after-swap, calm conversation).

## Open Questions
- **Paid price:** $9.99 a month, as v1's Lovers plan, or something else? This is needed before M2 Stripe setup.
- **What the recipient sees:** should the recipient ever see that coaching happened (for example a subtle "written with care" mark), or is that private to the sender? The Ohio State effect suggests keeping it private.
- **Diary and weekly report:** in the first v2 release, or after the composer is validated?
- **Hosting:** where Postgres and the web app run (for example Neon plus Vercel). This needs the founder's accounts.

## Success Criteria
- **M1:** a couple can sign up, connect, and the anxious partner sends a coached message in under 3 minutes from first open.
- **M1:** coaching suggestions appear within 3 seconds of tapping "How will this land?".
- **M1, tested:** the recipient gets the delivered text only. The original appears in their API responses only when it was shared and they have paid access, and drafts and suggestions never appear.
- **M1, tested:** a failed translation sends nothing unless the sender explicitly chooses "Send my words as written". A failed coaching pass never blocks sending.
- **M1, tested:** the 5 free translations hold under parallel sends, and a failed translation returns its slot. Coaching is refused for free users. Pairing enforces one partner each, and wrong codes are rate-limited.
- **M1, tested:** safety drafts produce no softening suggestions.
- **M2, tested:** a Stripe event delivered twice is applied once, a couple with an active subscription can't check out again, and cancellation and payment-failure transitions follow the billing rules.
- **Product signal:** of the first 3 real anxious-attacher users, at least 1 sends a message they say they would otherwise have kept to themselves.

## Distribution Plan
- **Web:** the Next.js app deployed to a managed host (Vercel or similar) with hosted Postgres. GitHub Actions runs typecheck, lint and tests on every push.
- **Mobile:** an Expo app in the same monorepo after the web launch, distributed through EAS Build to the Play Store and App Store. Deferred until the web composer is validated.

## Dependencies
- **Prerequisite:** rotate the Clerk secret key, then use a new Clerk key pair (or a new Clerk application) for v2. v1's exposed keys are not reused.
- The founder's own Anthropic API key, replacing the Emergent key.
- Stripe test keys (M2).
- A Postgres database, local install or hosted.

### R2-1 — consistency (blocking)

**Problem**

> The new constraint says unsent drafts never leave the sender's device, and Privacy says 'Drafts stay on the sender's device until sent', yet a coaching pass sends the current draft text to the API and on to Anthropic ('What the AI receives: the current draft text'), and AI suggestions are generated server-side. The invariant as written cannot hold for any coached message, so the test in Success Criteria has no well-defined target.

**Remedy**

> Restate the invariant precisely: drafts are sent transiently to the coaching endpoint and Anthropic for a pass, are never persisted server-side or logged, and never appear in any API response to the recipient. Align the Privacy bullet and the success-criterion test with that wording.

### R2-2 — consistency (blocking)

**Problem**

> Coaching caches results by draft hash so repeat taps do not count as a pass, but Privacy says 'AI suggestions are not stored'. A server-side cache stores suggestions (and a hash of the draft); a client-only cache cannot make the server skip metering unless the client simply does not call. Where the cache lives, how long it lives, and how it interacts with the atomic pass counter is undecided, and the privacy statement contradicts any server cache.

**Remedy**

> Decide the cache location: either client-side only (the client does not re-call for an unchanged hash, server meters every call it receives) or a server cache keyed by user plus hash with a short stated TTL. Update the 'AI suggestions are not stored' line to match.
